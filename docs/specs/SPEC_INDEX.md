## How to read this file

- **ID** — stable identifier. Never renumber an existing ID; new aspects get the next free number.
- **Parent Aspect** — the single aspect this one is organizationally nested under (drives the tree
  in §Dependency Tree).
- **Dependencies** — every aspect that must exist first, including the parent. An aspect with more
  than one dependency lists all of them here even though Parent Aspect names only the primary one.
- **Level** — `1 + max(level of every aspect in Dependencies)`. Level 1 = no dependencies (root).
- **Status** — one of `Not Started`, `In Progress`, `Completed`, `Blocked`, `Needs Review`. An
  aspect is `Blocked` whenever any aspect in its Dependencies column is not `Completed` — this is
  mechanical, not a judgment call. See [`CLAUDE.md`](CLAUDE.md) for the full rule.
- **Order** — the validated build/UX sequence number (§Recommended Implementation / UX Order).
  Order strictly respects Level and dependency validation (§Dependency Validation) — a lower Order
  number never depends on a higher one.

## Dependency Issues

Found while reconciling the source documents' presentation order against actual dependencies:

1. **Header Language Selector vs. Internationalization.** SRS §4 lists the language selector as
   part of the header, alongside search and the cart icon — implying it ships with basic
   navigation. But a language selector has no function until the Internationalization mechanism
   (A-021, SRS §4/§28) exists. **Correction:** split header into A-003 (core nav — logo, links,
   search entry, cart badge, ships early) and A-022 (language selector, a dependent of A-021,
   ships later). This is a real conflict in the source's flat presentation, resolved by splitting
   the aspect rather than forcing the whole header to wait for i18n or ignoring the dependency.

2. **Admin Data Exports vs. Orders/Quotes/Custom Requests.** SRS §19 and the Addendum §12 module
   checklist list "Data Exports" as a basic Admin module alongside Settings and Dashboard — as if
   it's foundational. But the Addendum §6-7 named export datasets (`Orders`, `Quotes`,
   `Custom_Requests`, `Payments`, `Downloads`) can't be *meaningfully* complete until those
   features (A-013, A-016, A-017) exist. **Correction:** A-005e's dependency list and Level (9)
   reflect the real data dependency, not its early mention in the flat module checklist.

3. **Admin Live Website Preview — dependency scope is genuinely unclear.** SRS §19/§12 name it as
   a basic Admin module, but by definition a "preview of the live website" depends on however much
   of the public site exists at the time — the source material never states a specific boundary
   (e.g., "must reflect Catalog and Home, but not yet Services"). **Marked `Needs Review`** per
   the instruction to flag rather than guess; placed conservatively near the end of the Order
   sequence (after every public-facing aspect) until Admin confirms the intended scope.

4. **Taebo's technical dependency level vs. recommended build order.** See the note under position
   28 above — not a conflict, but flagged so Order is never mistaken for "when to build it."

No dependent aspect was found positioned before its parent in either source document's own
narrative flow once these three items were corrected — the remaining presentation order in both
documents (SRS numbered sections 1–32, architecture's section order) is a *reading* order, not a
build order, and was not assumed to be one anywhere in this file.
