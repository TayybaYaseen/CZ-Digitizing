# Customer-site internationalization (i18n)

Implements [docs/specs/2026-08-28-16-internationalization.md](specs/2026-08-28-16-internationalization.md)
(aspect A-021) for the customer website (`apps/web`). The admin panel (`apps/admin`) is not
localized; it only edits the override rows described below.

## How it works

- **Strings** live in `apps/web/i18n/messages/<code>.ts`. `en.ts` is the source of truth. Every
  other file is typed `Messages`, so `pnpm --filter @czd/web typecheck` fails if any language is
  missing a key or has an unknown one. `pnpm --filter @czd/web i18n:check` additionally verifies
  that every translation keeps the same `{placeholders}` and `<tags>` as English.
- **Lookup:** components call `const { t } = useLocale()` (`apps/web/lib/locale-context.tsx`).
  Page metadata (`generateMetadata`) calls `await getServerTranslator()` (`apps/web/i18n/server.ts`).
  Keys are type-checked, e.g. `t('nav.home')`. Visible UI should use `useLocale()`, even in a
  component with no other client code. A server component only picks up a new language after
  `router.refresh()` finishes, so it would briefly show the previous language after a switch.
  - Interpolation: `t('orders.orderId', { id })` with `{id}` in the string. Numbers are
    locale-formatted.
  - Plurals: `key_one` / `key_other` (plus `_zero/_two/_few/_many` where a language needs them,
    e.g. Arabic and Russian), called as `t('products.designCount', { count })`.
  - Inline markup: `rich('auth.noAccount', { link: (chunk) => <Link …>{chunk}</Link> })` with
    `<link>…</link>` in the string. Never split a sentence into several keys.
  - Runtime keys (order status etc.): `tOr(\`orderStatus.${status}\`, status)`.
  - Dates and numbers: `formatDate`, `formatDateTime` and `formatNumber` from `useLocale()` (Intl).
    Bank-transfer PKR amounts deliberately stay in fixed `en-US` formatting (`formatPkr`) so the
    amount a customer transfers never varies by device.
- **Errors:** `ErrorBanner`/`errorMessage()` map the API's English error by exact message, then
  by stable `error.code`, to an `apiErrors.*` key (`apps/web/i18n/api-errors.ts`). Errors raised
  in the browser use `clientError('errors.someKey')`, which stores the key rather than English, so
  the message follows a later language switch. Form-field messages (zod schemas and the API's
  class-validator messages) are translated by `FormField` through `fieldError()`.
- **Loading:** each language is its own webpack chunk. The server renders only the active
  language's strings; the browser downloads another language only when the customer switches.
- **Admin overrides:** rows in `ui_translations` (edited at `/admin/settings/translations`) are
  fetched with `GET /api/translations/:locale?fallback=false` and layered on top of the bundled
  strings, so Admin can reword a string without a deploy. `fallback=false` matters: without it the
  API merges English rows in, which would overwrite translated text.
- **Languages table:** `GET /api/languages` hides a language whose `languages.is_enabled` Admin
  has switched off (English and the active language always stay visible). If that request fails,
  all 15 languages still show.

## Translation precedence

For the active language, each key resolves in this order (first match wins):

1. **Admin override** for that language (a `ui_translations` row with `locale = <active language>`).
2. **Bundled string** for that language (`apps/web/i18n/messages/<code>.ts`).
3. **Bundled English** (`en.ts`). This only fills a gap for a future partially-translated
   language; the typecheck keeps all 15 current languages complete.
4. The key itself (last resort, never reached for a valid key).

English override rows only affect English. They are never used as a fallback for another
language.

Where the merge happens:
- **First page load:** the server merges the Admin overrides before rendering (fetched per
  request, uncached), so the first HTML already shows the Admin's wording. There is no flash from
  the bundled text.
- **Language switch:** the browser loads the new language's bundle and its overrides together.

If the API is unreachable, the overrides are skipped and the bundled strings render.

Verified end to end through the Admin UI: the edited text showed on first load, after refresh,
after navigation, and after switching language away and back. Removing the row brought back the
bundled string.

**Admin UI limitation (not changed in this work):** the translations page lists only keys that
already have an English `ui_translations` row. Today that's the 20 seeded keys (nav, cart,
checkout, account, FAQ title, common). For a non-English language, each input is pre-filled with
the English row, not with the bundled translation customers actually see. Saving writes only the
fields that were edited. Any other key can be overridden through
`PUT /api/admin/settings/translations/:locale`.

## Persistence

1. Choosing a language writes the `czd_locale` cookie (1 year, `path=/`, `SameSite=Lax`).
2. The root layout reads that cookie **on the server**. The first HTML response already has the
   right text, `<html lang>` and `<html dir>`, so there is no English flash, no hydration mismatch
   and no post-load RTL flip. The language persists across navigation, refresh and return visits.
3. When the customer is signed in, the choice is also saved to `users.preferred_locale`
   (`PUT /api/account/preferred-locale`). At sign-in, a choice already made on this device wins
   and is saved to the account. With no choice on this device, the account's saved language is
   applied.
4. First visit with no cookie: English (spec AC-2). The browser's language is not auto-detected.

Trade-off: because the root layout reads a cookie, every route is rendered dynamically on the
server (`ƒ` in `next build`) instead of being prerendered. Pages were already client-rendered and
data-driven, so this adds server rendering per request but no client JavaScript.

## RTL (Arabic, Urdu)

- `<html dir="rtl">` is set server-side from the cookie and updated immediately on a switch.
- Direction-sensitive Tailwind classes use logical properties (`start/end`, `ms/me`, `ps/pe`,
  `text-start/end`, `border-s`), so the header, dropdowns, mobile drawer (slides in from the left
  in RTL), forms (password eye icon, error text), cards and badges mirror correctly. LTR renders
  exactly as before.
- Only direction-carrying glyphs are mirrored (`BackArrow`/`ForwardArrow`, lightbox chevrons, the
  "back" chevron icon). Logos, photos, the Taebo character and other icons are not flipped. The
  portfolio lightbox's arrow keys follow the visual direction.
- Admin-authored content (FAQ, product names, blog, testimonials, notifications, portfolio CV…) is
  rendered with `dir="auto"`, so English content inside an Arabic page keeps correct punctuation
  and alignment.

## What is translated and what is content

Everything that is UI chrome is translated: header, navigation, mobile menu, search, auth and OTP
flows, forms, validation, buttons, empty/loading/error/success states, cart, checkout,
bank-transfer, orders, downloads, account area, notifications UI, pricing and subscription,
quote and custom-request flows, footer, Taebo's UI, greeting, escalation text and quick actions,
aria-labels and alt text, and status labels (order, quote, custom-request, notification type and
channel).

**Database/Admin-authored content is shown as stored and is not machine-translated.** The data
model has no per-language columns for these fields:

| Entity / field | Notes |
|---|---|
| `designs.name`, `designs.description`, `designs.tags`, design sizes' `label` | catalog |
| `design_categories.name`, `design_subcategories.name` | catalog, filters, header search |
| `bundles.name`, `bundles.description` | catalog |
| `services.name`, `description`, `applications`, `process` | services pages, quote step 1 |
| `quote_questions.question`, `answer` | quote step 2 |
| `blog_posts.title`, `category`, `body` | blog |
| `embroiderer_tips.title`, `category`, `content` | tips (a `language_code` column already exists; the list view does not filter by it yet) |
| `faqs.question`, `answer`, `topic` | FAQ already requests `?language_code=<locale>` with English fallback (spec AC-5); only English rows exist today. Also shown in Taebo suggestions. |
| `testimonials.feedback`, `service_used`, `country`, `business` | customer-written, intentionally left as written |
| `about_content.heading`, `body` | about page |
| `home_sections.heading`, `description`; `header_media.heading`, `subheading`; `advertisements.heading`, `offer_text`, `cta_text` | home page promotions |
| `portfolio_items.title`, `description`, `category`, `software_used`, `embroidery_type` | portfolio |
| `subscription_plans.name`, `perks`; `credit_packages.name` | pricing |

| `apps/web/lib/portfolio-profile-content.ts` | CV-derived, source-traced text that must not be reworded (see that file's header). Only the section headings around it are translated. |

A multilingual content model (per-language rows or `*_translations` tables, plus Admin UI) is a
separate piece of work. The FAQ/Tips `language_code` pattern is the existing precedent.

## Emails are separate

Backend emails (`apps/api/src/email`, `apps/api/src/auth/templates`) are English only and don't
read `users.preferred_locale`. Website localization doesn't change them. Every customer email is
English:
- welcome email (after registration)
- login / new-device verification code, including a resent code
- forgot-password reset code
- magic login link
- "new login attempt" alert
- notification emails (order confirmed, payment received, files ready, receipt and quote
  updates), which reuse the English notification title and message
- quote-response emails
- freelancer account email

Localized emails are a separate backend task: pass the recipient's `preferred_locale` into each
template and add per-locale template strings.

## Adding or changing a string

1. Add the key to `en.ts` (group it under the page or feature namespace).
2. Add it to all 14 other locale files. The typecheck lists every file still missing it.
3. Use it: `t('namespace.key')`. Don't put customer-visible English in JSX.
4. Run `pnpm --filter @czd/web typecheck` and `pnpm --filter @czd/web i18n:check`.

Never translate: CZ Digitizing, Taebo, Machine Embroidery Designs, Vector Art, WhatsApp, file
formats (DST, PES, JEF, EXP, VP3, XXX, EMB), PKR/Rs.

## Adding a 16th language

Add it to `LOCALES` in `i18n/config.ts`, create `i18n/messages/<code>.ts` typed `Messages`, add
its loader in `i18n/messages/index.ts`, and insert a `languages` row (a migration, like
`20260930120000_add_remaining_ui_languages`). This is a code change and deploy. The earlier
DB-only path (spec AC-6) now only covers overriding strings for existing languages. The bundled
approach was chosen so every language ships complete, type-checked and server-rendered.
